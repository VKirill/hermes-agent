# Async agy cancellation was published outside the process-start fence

**Date:** 2026-07-16 13:39
**Files:** agent/agy_cli_client.py, tests/agent/test_agy_cli_client.py
**Severity:** high

## Problem

`AsyncAgyCLIClient.create()` set its per-request `cancellation_event` before entering `AgyCLIClient._active_process_lock`, while process startup checked that event, called `Popen`, and registered the child under the lock. Cancellation state and process lifecycle state therefore had different linearization points. A forced interleaving could publish cancellation while process startup was already acting on a stale `is_set()` result.

## Root Cause

The cancellation path treated `threading.Event.set()` as both an immediate signal for queue polling and the authoritative process-start decision, but the active-process registry used a separate lock-protected transaction. Because the event mutation happened before `_cancel_active_process()` acquired the registry lock, process startup could observe a stale event state inside its critical section while cancellation was blocked waiting to inspect the registry.

## Solution

Removed the out-of-band event mutation from the async facade. `_cancel_active_process()` now sets the request event and snapshots every matching registered child inside `_active_process_lock`, the same fence used by the final cancellation check, `Popen`, and registration. The resulting order is linearizable: cancellation wins the fence and prevents `Popen`, or startup wins the fence, registers the child, and cancellation applies the existing terminate→kill→wait path to that registered process.

Added deterministic regressions using the real `AsyncAgyCLIClient`: one proves cancellation is not published while the process-start fence is held, and one proves that cancellation winning the fence produces no `Popen`, no child side effect, no running lease, and no retained workspace.

## Prevention

- A cancellation token that controls resource creation must be mutated under the same fence as the final pre-create check and resource registration.
- Treat check→create→register as one transaction; cancellation must either precede the transaction or observe the registered resource afterward.
- Race tests should use barriers to force both arbitration orders and assert external effects, registry/lease state, and cleanup.
- Keep process termination and reaping outside the registry lock after taking a stable snapshot to avoid lock-held waits.
