## Слой 1 — Upstream user-доки (часть PR, обязательно)

**Файлы (пути проверить на момент написания — структура доки могла измениться):**
- `website/docs/user-guide/messaging/telegram.md` — секция «Per-topic profile isolation».
- Дока профилей (найти: `website/docs/**/profiles*` или раздел про профили) — расширить
  про изоляцию и per-profile конфиг.
- Возможно `cli-config.yaml.example` — пример блоков `mcp_servers`/`enabled_toolsets`
  в профильном конфиге (по их чек-листу PR обновляют example-конфиг).

**Что описать:**
1. **Концепт:** один бот, топики привязываются к профилям через `/profile <name>`;
   каждый профиль = полностью изолированное окружение. Непривязанные топики — как раньше.
2. **Команды:** `/profile` (показать/список), `/profile <name>` (привязать),
   `/profile default|reset|clear` (снять).
3. **Раскладка профиля** `~/.hermes/profiles/<name>/`:
   ```
   config.yaml   # model, mcp_servers, enabled/disabled_toolsets, agent.max_turns, user_profile_enabled: true
   SOUL.md       # личность профиля
   .env          # ключи провайдеров — ПОЛНЫЙ набор (строгий secret-scope, без фолбэка на главный)
   skills/       # свои skills профиля
   memories/     # авто, изолированная память (MEMORY.md)
   sessions/     # авто, изолированный state.db
   ```
4. **Ключи `config.yaml` на профиль:** `model`/`provider`, `mcp_servers`,
   `enabled_toolsets`/`disabled_toolsets`, `agent.max_turns`, `user_profile_enabled: true`.
5. **MCP на профиль:** объявляются в профильном `config.yaml`; **одноимённые серверы у
   разных профилей — ОК** (идентичный конфиг → общее соединение; разные токены → раздельные);
   `mcp_servers.<name>.tools.include/exclude` — сузить тулзы; `enabled: true|false` — выкл.
6. **Креды (строго):** профильный `.env` должен быть полным — ключа нет → **видимая
   ошибка**, без тихого фолбэка на `~/.hermes/.env`. (Объяснить, почему так — безопасность.)
7. **Грабли в доку:**
   - macOS + облачные маунты (iCloud/Google Drive/FUSE) → профильный home держать
     **локально**, иначе дедлок I/O.
   - `user_profile_enabled: true` для routed-агентов (дефолт `false`).
   - **Gateway-тулзы/MCP НЕ прокидываются** в профиль автоматически — профиль объявляет
     своё в своём `config.yaml`.
8. **Полный рабочий пример — 2 профиля:**
   ```yaml
   # ~/.hermes/profiles/coder/config.yaml
   model: { default: deepseek-v4-pro/deepseek }
   user_profile_enabled: true
   mcp_servers:
     github: { command: npx, args: ["-y","@modelcontextprotocol/server-github"],
               env: { GITHUB_TOKEN: "${GH_WORK}" } }
   # ~/.hermes/profiles/trader/config.yaml
   model: { default: minimax-... }
   user_profile_enabled: true
   mcp_servers:
     polymarket: { command: npx, args: ["-y","@x/polymarket-mcp"] }
   ```
   В Telegram: топик «Код» → `/profile coder`, топик «Трейдинг» → `/profile trader`.
9. **Миграция/совместимость:** поведение непривязанных топиков и `multiplex_profiles: false`
   без привязок — без изменений (zero-regression).
10. **Диагностика:** `hermes profile audit-isolation` — проверить, что профиль не
    пересекается с главным.

## Слой 2 — Bundled Hermes-скилл (опционально, отдельный follow-up)

**Идея:** Hermes агентный → дать **скилл, который агент подгружает и сам проводит юзера
по настройке изолированного профиля.** Не блокирует основной PR.

- **Имя:** напр. `setup-profile-isolation` (или `configure-profile`).
- **Где живёт:** bundled-скиллы (найти каталог: `skills/` или `optional-skills/` —
  свериться с тем, как лежат штатные SKILL.md). NB: skills теперь per-profile, так что
  это **глобальный/bundled** скилл, не профильный.
- **SKILL.md — структура:** `name`, `description`, `when-to-use`, затем шаги, по которым
  агент ведёт юзера:
  1. Создать профиль (`hermes profile create <name>` / scaffold, если есть — см. #52609).
  2. Заполнить `config.yaml` по шаблону (model, mcp_servers, toolsets, user_profile_enabled).
  3. Положить `SOUL.md`, `.env` (полный набор ключей), `skills/`.
  4. Привязать топик: `/profile <name>` в нужном Telegram-топике.
  5. Проверить: `hermes profile audit-isolation` + smoke (память/файлы/SOUL пишутся в профиль).
- **Поставка:** **отдельным PR** (скиллы обычно мёрджат отдельно) — или просто положить
  локально себе, без upstream.
- **Связь:** ссылается на те же грабли/ограничения, что и слой 1 (single source — спека).

**Чек-лист слоя 2 (если делаем):**
- [ ] `SKILL.md` написан, шаги проверены вручную.
- [ ] Учтена граница «gateway-MCP не прокидываются».
- [ ] Решено: upstream-PR vs локально.

## Слой 3 — Локальная память ассистента (делает ассистент, ПОСЛЕ настройки)

**Что:** обновить память про сетап (`hermes-agent-setup.md`) и при необходимости завести
отдельную запись:
- Новая модель изоляции: что именно изолируется на профиль (config/память/SOUL/.env/
  skills/sessions/MCP) и как это включается (`/profile` + профильный `config.yaml`).
- **Реальный расклад юзера** после настройки: какие профили заведены, какие MCP-серверы
  у каждого, какие топики куда привязаны, какие модели.
- Грабли, которые всплыли именно у него (строгие креды, FUSE, и т.п.).

**Когда:** ПОСЛЕ того как юзер реально настроит профили (до этого детали поплывут).
**Кто:** ассистент (не реализующий агент). Это не upstream — только для будущих сессий.
